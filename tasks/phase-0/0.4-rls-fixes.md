# 0.4 RLS fixes

## Goal
Appointments are created only through `book_appointment`. Staff see and change data only at their
own centers. Users write only their own avatar files and see only their own slot locks.

## What the migration does
1. **appointments INSERT**: dropped `users_insert_own_appointments`; revoked INSERT from anon/authenticated.
   Booking is only through `book_appointment`, which now checks that the service belongs to the lock's
   clinic. `lock_slot` now checks login, a non-past date, that the clinic exists, and that the doctor is
   active at that clinic.
2. **Staff scope via `staff_centers`**:
   - `appointments`: SELECT and UPDATE are limited to the staff member's centers. UPDATE's WITH CHECK
     also stops moving a row to another center. Admin keeps its own SELECT/UPDATE policies.
   - The same scope for the queue tables staff write to directly (same hole):
     `center_queue_settings`, `center_daily_tokens`, `doctor_queue_settings`, `queue_updates`.
3. **profiles**: staff see only patients with an appointment at one of their centers
   (`private.staff_can_view_profile`); admin sees all. There's no staff UPDATE policy on profiles,
   so nothing to scope there.
4. **storage.objects (avatars)**: insert, update and delete only under `<auth.uid()>/`. The app already
   uploads to `${userId}/avatar.<ext>`, so no code change.
5. **slot_locks**: SELECT only own locks.
6. **Views**: `current_token_view`, `queue_view` now use `security_invoker = true`.

## Behavior notes
- The legacy `getAvailableSlots` (BookAppointmentScreen) read other users' locks to hide locked slots;
  it now sees only its own, and a clash surfaces as "Slot just taken" from `lock_slot`. That screen goes
  away in 0.5. The main flow (`SelectSlotScreen` → `get_available_slots`) is unaffected.
- Doctors still have no policy to read their patients' `profiles` rows directly. That's unchanged from
  before; their dashboards use the doctor RPCs.

## Follow-up: `20261021082250_access_followups.sql` (owner decisions)
1. **audit_logs**: staff read and insert only rows whose appointment is at one of their centers, and
   insert only as themselves. Admin reads all. Patients read none.
2. **notifications**: no client INSERT (policies dropped, privilege revoked). The notification trigger
   functions (`create_notification_on_appointment`, `create_notification_on_cancel`, `notify_on_cancel`)
   are now SECURITY DEFINER. Before, they inserted *as the user* whose action fired them, so a staff
   cancel through a direct UPDATE would have failed.
3. **avatars**: broad SELECT removed. Read, insert, update and delete only via
   `private.can_manage_avatar_path`: your own `<uid>/` folder, or `doctors/<doctor_id>/` if you are that
   doctor or an admin. Display uses public URLs, which need no policy. The owner-only SELECT stays
   because Storage upserts and the doctor-photo `.list()` check need it.
   **This also fixes a 0.4 regression**: doctor photos live under `doctors/<doctor_id>/`, which the 0.4
   own-folder rule blocked. My 0.4 tests only covered patient avatars.
