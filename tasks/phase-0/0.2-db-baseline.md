# 0.2 DB baseline (no schema change)

## Goal
One migration in `supabase/migrations/` that rebuilds the current live schema from nothing, so that
`supabase db reset` on the local stack gives an exact copy of production's schema. All loose SQL is
archived. Production is not changed.

## Findings (read-only inspection, 2026-10-21)
- **Tooling missing on this machine:** no `supabase` CLI, no Docker runtime, no `supabase/config.toml`
  (the project was never `supabase init`-ed), and nothing is linked.
- **Live migration history doesn't match the repo.** Live has **49** entries (`20260509152744` …
  `20260921191825`), mostly applied through the dashboard or MCP. The repo has **8** files with different
  version numbers. For example, `restrict_appointment_completion_to_doctor` is `20260921130000` locally and
  `20260921190739` live.
- These repo migrations are **not** in live history:
  - `add_doctor_reviews` and `add_visit_summaries` (matches the audit; they're handled in 0.6)
  - `20260716_security_cleanup`, `hyderabad_hospitals_map_seed` and `repair_clinic_image_urls`
    (maybe run by hand in the SQL editor; the baseline will show what's actually there)
- `20260716_security_cleanup.sql` has an 8-digit version, which the CLI can't order reliably against
  14-digit versions.
- Live extensions: `pgcrypto`, `uuid-ossp`, `moddatetime`, `pg_stat_statements`, `hypopg`,
  `index_advisor`, `supabase_vault`, and **`pg_net` installed in `public`** (an advisor warning; for
  later). `pg_cron` is **not** installed. **It gets enabled in Phase 1D.** Until then, 0.3 only removes client access to
  `cleanup_stale_appointments`; nothing schedules it.
- 57 loose `.sql` files are in `supabase/`.

## Approach
### Why not a plain `supabase db pull`
`db pull` first compares local migration files against the live history table. With 49 unknown remote
versions it stops and tells you to run `supabase migration repair`, which **writes to production's
`supabase_migrations.schema_migrations`**. That breaks the "no writes to live" rule, so here's the plan:

1. Build the baseline with **`supabase db dump`** (pg_dump in Docker, read-only). It doesn't check history.
2. `pg_dump --schema public` misses Supabase-managed schemas, so I add the app's objects in
   `auth`/`storage` from a read-only `db dump --schema auth,storage` (only `CREATE TRIGGER … ON auth.users`
   and `CREATE POLICY … ON storage.objects`, plus any `storage.buckets` rows the app needs), plus the
   `supabase_realtime` publication membership.
3. Prove it matches: `supabase db reset` locally, then **`supabase db diff --linked`**. That builds a
   shadow DB from the local migrations and compares it with live (read-only on live). Target: no diff.
4. Aligning live's history table is **your** step, done later (command below).

### Two fixes needed to make the baseline exact
1. **Grants.** The local stack's default privileges auto-grant ALL to anon/authenticated/service_role
   on every new object in `public`. pg_dump only records the GRANTs production has, so local came out
   *more permissive* than live (diff: ~200 REVOKE lines). Fix: revoke those defaults right after the
   extensions in the baseline. The dump's own `ALTER DEFAULT PRIVILEGES` lines restore live's defaults at the end.
2. **CRLF.** 17 function bodies on live use Windows line endings (369 CR bytes, from the SQL editor).
   The first assembly normalised them, and the diff tool flagged all 17. Fix: byte-preserving
   assembly, plus `.gitattributes` `-text` on the baseline so git never rewrites it.

## Facts found in the live schema (input for 0.3/0.4/0.6, NOT changed here)
- Most functions still have the built-in `EXECUTE` for **PUBLIC** (e.g. `start_service`, `book_appointment`
  show `=X/postgres`). anon is a member of PUBLIC, so revoking from `anon` alone isn't enough;
  0.3 must `REVOKE ... FROM PUBLIC` too.
- `anon` and `authenticated` have **ALL** on `public.appointments` (RLS is the only gate).
- `service_role` has only REFERENCES/TRIGGER/TRUNCATE/MAINTAIN on `appointments` (and on ~20 tables), with
  no SELECT/INSERT/UPDATE/DELETE. The `send-queue-notification` Edge Function uses the service role,
  so it may already fail on live. Check in 0.6.
- `avatars` policies only check `bucket_id`: any signed-in user can update or delete any avatar (0.4).
- Realtime publication: `doctors`, `notifications`, `queue_updates` only; `appointments` and both
  `*_queue_settings` tables are missing (0.6).
