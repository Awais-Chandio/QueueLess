# 0.5 Auth cleanup

## Goal
The Firebase phone-login bridge can't be used. The legacy booking screen and its direct-insert path
are gone; every booking goes through the normal flow (SelectSlot → PatientDetails → ConfirmBooking).
Firebase Cloud Messaging is untouched.

## Findings
- **The bridge is an account-takeover hole, not just legacy code.** `authService.bridgeFirebaseUserToSupabase`
  signs phone users into Supabase as `phone-<firebaseUid>@phone.queueless.com` with the password
  `fb-phone-auth-<firebaseUid>-a1b2c3d4e5f6g7h8_queueless_phone_auth_salt`, built on the client from a salt
  that ships in the app. Anyone who learns a phone user's Firebase UID can sign in as them with plain
  email+password, **whether or not the screens are reachable**. Disabling the bridge stops new accounts;
  existing ones need action on the server (see "Owner actions").
- `PhoneLogin` / `OTPVerification` are registered in `AuthNavigator`, but nothing navigates to them
  (dead but shipped).
- The only route to the legacy `BookAppointmentScreen` is the "Book Token" button on `QueueStatusScreen`
  (doctor queue view). It always has `doctorId`, and `centerId`/`serviceId` only sometimes.
- `appointmentService.createAppointment` / `lockSlot` / `unlockSlot` / `getAvailableSlots` and
  `appointmentStore.createAppointment` are used only by that screen. `lockSlot` inserted into
  `slot_locks` directly; `createAppointment` went through RPCs since 0.4.
