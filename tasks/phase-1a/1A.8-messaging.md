# 1A.8 Messaging ledger

## Goal
Each clinic has a prepaid message balance, and every SMS/WhatsApp message is logged with its recipient,
template, status and cost. Sending is Phase 1D; this is the data model and the one safe way to spend credits.

## What the migration adds
- **`message_credits (organization_id PK, balance ≥ 0)`**: one row per organization (backfilled; new
  organizations get one by trigger), starting at 0.
- **`message_log`**: `organization_id`, `appointment_id` (optional, `SET NULL`), `channel` (`sms | whatsapp`),
  **`to_phone`**, `template`, `status` (`queued | sent | delivered | failed`), `cost` (credits),
  `provider_message_id`, `error`, timestamps.
- **`charge_message_credits(org, channel, to_phone, template, cost, appointment_id?)`**: server-only
  (`service_role`; refuses any client session). It checks the plan module (`sms` / `whatsapp`), that the
  appointment belongs to that organization, and the phone format. It then **debits and logs in one statement
  pair, or fails with `PT402` and changes nothing**. The conditional `UPDATE … WHERE balance >= cost` means two
  concurrent sends can't spend the same credit.

## Decisions (safest option)
- **`to_phone`, not `to`**: `to` is a reserved word in SQL and would need quoting in every query and function.
- **Credits are integers** (whole credits, not rupees). Pricing per credit is a billing decision.
- **Only owners and platform admins read** credits and the log. Receptionists and doctors don't, because the log
  holds patients' phone numbers.
- **No client writes at all**, top-ups included (platform admin / billing, Phase 1C). `service_role` gets only what the
  Phase 1D sender needs: read the balance, read the log, update `status / provider_message_id / error / updated_at`.
  It **can't rewrite cost**.
