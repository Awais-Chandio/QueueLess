# 1A.1 Tenants: organizations

## Goal
A clinic business is an **organization** (the SaaS tenant). Every service center belongs to exactly one
organization, and every business table can be traced to one.

## What the migration does
1. **Preflight**: fails before changing anything if an appointment points at a deleted center (it couldn't be
   given an organization). The production preflight query is in the Phase 1A summary.
2. **`organizations`**: `name`, `slug` (unique, `a-z0-9-`), `timezone` (default `Asia/Karachi`, validated),
   `status` (`active | suspended`), `is_legacy`, timestamps. RLS on. Only platform admins can read it
   in this step (1A.2 adds members). No client writes.
3. **`service_centers.organization_id`**: FK `ON DELETE RESTRICT`, indexed, **NOT NULL** after backfill.
4. **Backfill**: one default organization **per existing center** (`is_legacy = true`, same name, slug
   `<name>-<8 hex>`).
5. **New centers** without `organization_id` (the admin app's center form, the seed) get a default
   organization from a `BEFORE INSERT` trigger, so the existing app needs no change. Moving a center to
   another organization: platform admin / server only.
6. **Missing center foreign keys**: `appointments.center_id` (validated) and `center_queue_settings.center_id`
   (validated only when there are no orphan rows, otherwise left `NOT VALID` with a warning).

## Decisions (safest option)
- **One organization per existing center, not one for all.** The live centers are different hospitals; one
  shared tenant would let each see the others' data the moment org-level roles exist.
- **The trigger is created before the backfill**, so a center inserted while the migration runs is covered either way.
- **Deleting a center with appointments now fails** (FK `NO ACTION`) instead of silently orphaning medical
  records. In the admin app, "delete center" shows the database error for such centers. Centers
  without appointments still delete (with their doctors, services, staff links, as before).
- `center_queue_settings` orphans aren't deleted. They're harmless, and the migration never deletes data.

## Table → organization map
| Path | Tables |
|---|---|
| direct | `service_centers.organization_id` (1A.4+: `patients`, 1A.7+: `org_*`, 1A.8: `message_*`) |
| center → org | `appointments`, `services`, `doctors`, `staff_centers`, `slot_locks`, `center_daily_tokens`, `center_queue_settings` |
| doctor → center | `doctor_schedules`, `doctor_leaves`, `doctor_services`, `doctor_reviews` |
| appointment → center | `queue_updates`, `audit_logs`, `visit_summaries` (→ `prescription_items`) |
| not tenant data | `profiles`, `device_tokens`, `notifications` (a person's account across clinics), `plans` (global, 1A.7) |
| loose | `doctor_queue_settings` (keyed by doctor id, no FK: the legacy `sync_live_queue_after_appointment_change` trigger also writes rows keyed by a **center** id, so an FK would break every appointment write; see "Found") |

A pgTAP check walks the FK graph and fails if any other public table can't reach `organizations`.

## Found (not changed here)
- `sync_live_queue_after_appointment_change` passes `center_id` to `refresh_live_queue(p_doctor_id …)`.
  It inserts a junk `doctor_queue_settings` row per center and never writes `queue_updates`. Behaviour is
  unchanged in 1A. Fix it in the queue rebuild.
