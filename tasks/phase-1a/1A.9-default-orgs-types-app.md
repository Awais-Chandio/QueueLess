## What the migration does
1A.1 already created one default organization per center (the NOT NULL needed it). This last migration:
1. **Repairs** anything an earlier backfill could have missed: memberships from `staff_centers` / `doctors`, a Free
   subscription, entitlements, a credit row. Idempotent, no-op on a clean run.
2. **Verifies** and aborts (its transaction rolls back) on any of: centers sharing a default organization;
   staff/doctor accounts without their membership; organizations without subscription / entitlements / credits;
   appointments whose patient is in another organization; appointments without a public code.

## App changes (only what was needed)
- **No query changes were needed.** The existing screens keep working because the database adapts:
  - `book_appointment` → `patient_id` filled by trigger; source defaults to `app`.
  - Staff dashboard reads `appointments_full`, whose `patient_name` now covers guests. `enrichAppointments`
    already skipped missing `user_id`s.
  - Doctor screens read names from `get_doctor_today_appointments` / `get_doctor_recent_patients`, now guest-aware.
  - Direct updates the app makes (check-in, call, cancel, skip, complete, reschedule) are all in the 1A.3 column grants.
  - Admin writes to `staff_centers` / `doctors` / `profiles.role` keep memberships in sync by trigger.
- Type only: `AppointmentFull.user_id` nullable. `database.types.ts` isn't imported by the app (the client is
  untyped), so the regeneration can't break the build.
- **The Android app needs no new release** for 1A.
