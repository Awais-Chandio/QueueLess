# 1A.5 Tokens

## Goal
Queue tokens that don't need an app account or a time slot: receptionist walk-ins and anonymous QR joins,
on the same numbering as app bookings.

## What the migration adds
1. **`appointments.source`** `walk_in | qr | online | app`, NOT NULL, default `app` (all existing rows, and
   `book_appointment` keeps writing `app` without changes).
2. **`appointments.public_code`**: 8 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0/O/1/I),
   from `gen_random_bytes` (40 bits, uniform because 256 % 32 = 0). Unique index, NOT NULL, set by a
   `BEFORE INSERT` trigger with a collision re-roll. Existing rows backfilled (duplicates re-rolled before the
   index is built). Clients can't update it (not in the column grants from 1A.3).
3. **Time slot optional**: tokens have `appointment_time = NULL`. `scheduled_at` stays NOT NULL and holds the
   **issue time**: the staff dashboard filters "today" by `scheduled_at`, so walk-ins show up there unchanged.
4. **`issue_token(p_doctor_id, p_name, p_phone, p_source default 'qr')`** (SECURITY DEFINER, `anon` + `authenticated`):
   | Caller | Sources | Phone | Limits |
   |---|---|---|---|
   | staff of the doctor's center (owner/receptionist), platform admin, server | `walk_in`, `qr`, `online` | optional | none per phone |
   | anyone else, incl. anon | `qr`, `online` (`app` when signed in) | required | **3 per phone per organization per day** (also 3 per account); refused while the doctor is on leave |
   - Token number from the **existing per-doctor trigger** (`MAX + 1` under an advisory lock), so tokens and
     app bookings share one sequence.
   - Date = the **organization's local today** (`organizations.timezone`).
   - Walk-in/QR → `checked_in` (the person is at the clinic); online/app → `confirmed`.
   - Service: the doctor's first service at the center, else the center's first (`appointments.service_id` is
     NOT NULL and the token API has no service parameter).
   - Patient: a signed-in patient joining under their own name uses their account record. Otherwise the
     guest with the same phone + name (case-insensitive), else a new guest. Signed-in public joins keep
     `user_id`, so the token shows up in their app.
   - Returns `public_code`, `token_number`, `people_ahead`, `eta_minutes`; `appointment_id` only to staff or
     the signed-in owner (never to anon).
   - Errors: `22023` bad input, `42501` not allowed, `PT404` unknown/inactive doctor, `PT403` suspended clinic,
     `PT409` doctor on leave / no service, `PT429` limit. PostgREST maps `PTxxx` to that HTTP status.
5. **`private.token_progress(appointment)`**: `people_ahead` = waiting tokens (`pending/confirmed/checked_in`)
   with a lower number in the same queue that day; `current_token` = the one being served, else the last completed;
   `eta_minutes = people_ahead × average consultation time` (doctor setting, default 10).
6. **`cleanup_stale_appointments`**: slot rules now skip tokens (a token never "misses its 15-minute window").
   New rule: tokens still open after their clinic's day ended: waiting → `expired`, `called` → `no_show`.
7. `appointments_full` gains `source`, `public_code` (last columns).

## Decisions (safest option)
- **The rate limit is a private log table** (`private.public_token_joins`, no API access), not a count over
  patients. It counts the phone the caller *typed*, so switching names or accounts doesn't reset it. An advisory
  lock serializes concurrent joins from one phone. "Per clinic" = per **organization**, the stricter reading.
- **The limit counts successful joins only**, and staff are never limited (the receptionist is the fallback
  when a family hits the limit).
- `user_id` is **NULL on staff-issued tokens**, even if the receptionist is signed in.
- Public joins are refused while the doctor is on leave; staff can still issue (their call).

## Found (not changed)
- **`cleanup_stale_appointments` rules A/B were already broken**: they set `confirmed → no_show` and
  `called/in_progress → expired`, which `validate_appointment_status_transition` rejects. So one late booking
  aborts the whole run. Nothing schedules it (no pg_cron), so production never noticed. Left as is because
  scheduling and fixing it is Phase 1D. The new token rule only uses allowed transitions.
- Doctor screens use `CURRENT_DATE` (UTC) for "today"; tokens use the clinic's date. Tokens issued between
  00:00 and 05:00 Pakistan time show up in the doctor's "today" list from 05:00. Align in Phase 1B.

## Known risk (Phase 1B)
Phones aren't verified, so a script can still use many phone numbers. On the free plan the 30/day cap
bounds the damage (staff can cancel spam tokens, which frees the cap; see 1A.7). Add an edge rate limit
(IP / Turnstile) or OTP on the public join page before the QR page is published.
